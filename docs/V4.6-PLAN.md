# v4.6 计划（离线整理版，服务器恢复后照此执行）

状态：v4.5 实测 —— `metadata` 解密成功 ✓、`spblob` 找到 ✓、keystore2 正常 ✓、UI 与解密界面正常 ✓；
**唯一卡点：gatekeeper 校验失败（`verify_legacy` → `ret: -45`）**，导致拿不到 auth token，synthetic password 无法解封。

## 一、gatekeeper `-45` 的根因（结论）

### 1.1 为什么 v4.5 的"随机 challenge"没生效

**改错了调用点。** `system/vold/Decrypt.cpp` 里有**两处** `IGatekeeper::verify` 调用：

| 位置 | 代码 | 何时被走到 |
| --- | --- | --- |
| `Decrypt_User()` 的 legacy 分支（上游 `android-12.1` 第 924-950 行，我们树里约 1078 行） | `gk_device->verify(user_id, 0 /* challange */, curPwdHandle, enteredPwd, cb)` | 只有**没有** `/data/system_de/<user>/spblob` 目录时才走 |
| `Decrypt_User_Synth_Pass()` 的 `using secdis to decrypt spblob` 分支（上游第 **775** 行） | `gk_device->verify(fakeUid(user_id), 0 /* challenge */, pwd_handle_hidl, enteredPwd, cb)` | **本机走的就是这里**（recovery.log：`password type: PIN` → `Using synthetic password method` → `using secdis to decrypt spblob` → `GateKeeper response error`） |

v4.5 的 A1 补丁打在**第一处**（legacy 分支）→ 本机流程根本不会执行到它 → 日志当然毫无变化。

另外：两处上游代码传的都是 `0 /* challenge */`。所以 **challenge 的值很可能不是 `-45` 的原因**（厂商 HAL 的 `verify` / `verify_legacy` 选择由 SPU 决定，见 1.2）。

### 1.2 `-45` 的真正来源：SPU（spss）固件加载失败 → HAL 退化到 legacy → TA 不支持 legacy

厂商 HAL 里同时存在两个实现（`strings` 证实，见 `android.hardware.gatekeeper@1.0-impl-qti.so`）：

```
_ZN19GatekeeperHalDevice6verifyEjmPKhjS1_jPPhPjPb            ← verify()        （现代路径，走 SPU）
_ZN19GatekeeperHalDevice13verify_legacyEjmPKhjS1_jPPhPjPb    ← verify_legacy() （legacy 路径）
_ZN14keymasterutils14KeymasterUtils8spu_initEv               ← spu_init()
_ZN14keymasterutils14KeymasterUtils8isLegacyEv               ← isLegacy()
vendor.gatekeeper.disable_spu                                 ← 相关属性
```
`libkeymasterdeviceutils.so` 里的相关字符串：
```
SPU is not available
SPU available
QSEECom_send_cmd failed for spu init
/vendor/firmware_mnt/image          ← ★ 固件目录
```

v4.5 的 logcat 直接给出了这条因果链：

```
I spss_utils [spss_probe]: Probe completed successfully, [spss1p]      ← 内核驱动在，探针 OK
E ueventd : firmware: attempted /vendor/firmware_mnt/image/ipa_fws.mdt,
            open failed: No such file or directory                     ← ★ 固件目录不存在
gatekeeper@1.0-: avc denied { read write } for name="spss_utils" ... permissive=1
            （真正打开了 /dev/spss_utils，permissive 所以不是权限问题）
E KeymasterUtils: SPU is not available                                  ← spu_init 失败
E KeymasterUtils: IsSbKmAvailable failed
E GatekeeperHalDevice: verify_legacy                                   ← 于是退化到 legacy
E GatekeeperHalDevice: ret: -45                                        ← 该 TA 不支持 legacy 指令（EOPNOTSUPP）
keystore2: enforcements.rs:616: No suitable auth token found.           ← 没有 token
```

**结论**：recovery 只把 modem 分区挂到 `/firmware`，而内核/ueventd 按 `/vendor/firmware_mnt/image/...` 取固件 → SPSS(SPU) 固件加载失败 → `spu_init` 失败 → HAL 用 legacy 实现 → 该机 TA 不实现 legacy verify → `-45`。v4.5 的 challenge 补丁与此无关。

### 1.3 v4.6 的修法（首选，代价极小）

在 `recovery/root/init.recovery.qcom.rc` 里，把 modem 分区**同时**挂到 HAL/ueventd 期望的路径（`on fs`，早于 HAL 启动）：

```rc
# v4.6: SPSS/SPU 及其他固件由内核经 /vendor/firmware_mnt/image 请求；
# recovery 之前只挂了 /firmware，导致
#   "ueventd : firmware: attempted /vendor/firmware_mnt/image/ipa_fws.mdt, open failed"
# 从而 gatekeeper 无法初始化 SPU，退化到 verify_legacy -> ret -45。
mkdir /vendor/firmware_mnt 0755 root root
mount /dev/block/bootdevice/by-name/modem /vendor/firmware_mnt
```

（等价写法：`symlink /firmware /vendor/firmware_mnt`，但要确保在 `/vendor` 可写且挂载完成后执行。推荐直接再挂一次，语义最清晰。）

**验证方法**（服务器恢复后一次出包即可判定）：
1. logcat 里 `ueventd : firmware: attempted /vendor/firmware_mnt/image/...` 应变为**加载成功**（不再有 `open failed`）；
2. `KeymasterUtils: SPU available`（取代 `SPU is not available`）；
3. `GatekeeperHalDevice:` 应变成**现代 `verify`**（不再出现 `verify_legacy`），`ret` 为 0；
4. recovery.log 应出现 `GateKeeper status ok`，随后 `failed to unwrapSyntheticPasswordBlob` 消失；
5. 最终 `/data` 挂载成功、`twrp.user.0.decrypt=1`。

### 1.4 备选/并行的两处小改（防御性，非必需）

1. 把 v4.5 的 challenge 补丁**也**打在真正的调用点（上游 `Decrypt_User_Synth_Pass` 第 775 行那一处），与我们树的行号对齐后一起提交；即使 challenge 不是主因，也不会有坏处。
2. 若 SPU 仍起不来：检查 `/dev/spss_utils` 是否存在、`spss_utils` 驱动探针是否 OK（v4.5 已证 OK）、`/firmware/image/` 下是否有 `spss*` 固件（`ls /firmware/image | grep -i spss`）。
   `vendor.gatekeeper.disable_spu` 属性**不建议乱设**：它只会把 HAL 更牢固地推向 legacy，而本机 TA 恰好不支持 legacy。

## 二、能不能"绕过 gatekeeper"？（结论：不能）

源码流程（TWRP `system/vold/Decrypt.cpp`，上游 `android-12.1`）：

```cpp
// Decrypt_User_Synth_Pass(), "using secdis to decrypt spblob" 分支
gk_device = IGatekeeper::V1_0::IGatekeeper::getService();
...
gk_device->verify(fakeUid(user_id), 0, pwd_handle_hidl, enteredPwd, cb);   // 775
    // 回调里：把 TA 返回的 hw_auth_token_t 转成 HardwareAuthToken
    auto service = IKeystoreAuthorization::fromBinder(...);
    service->addAuthToken(authToken);                                     // 801-803
...
secret = android::keystore::unwrapSyntheticPasswordBlob(spblob_path, handle_str, user_id,
             application_id, PASSWORD_TOKEN_SIZE + SHA512_DIGEST_LENGTH, auth_token_len);  // 819
```

要点：
* gatekeeper 的产物不是"校验通过/不通过"，而是一个**由 TEE 里 gatekeeper TA 用 HMAC 签名的 `hw_auth_token_t`**；TWRP 把它交给 **keystore2 的 `IKeystoreAuthorization::addAuthToken`**，keystore2 再让 keymaster/keymint TA 校验签名与时间戳。
* `unwrapSyntheticPasswordBlob()` 解封 spblob 用的 keymaster key 是 **auth-bound** 的（`KM_TAG_USER_SECURE_ID` / `AUTH_TIMEOUT`），因此必须带上**有效**的 auth token —— 这正是
  `keystore2: enforcements.rs:616: No suitable auth token found` 与 `Error::Km(KEY_USER_NOT_AUTHENTICATED)` 的含义。
* 代码里**没有任何**"无 token 解 spblob"的分支；token 的 MAC 由 TA 生成，软件无法伪造。

**所以：gatekeeper 必须能工作。** "直接用密码 + keymaster 解 spblob" 在本机上不可行。
（也不要尝试绕过 `/metadata/vold/metadata_encryption/key/keymaster_key_blob`：那只是 **metadata（设备级）** 的密钥，v4.5 已经解开了 ✓；它解不开用户的 **CE（凭据级）** 存储，CE 密钥就在 spblob 里、且被 auth-bound keymaster key 包着。）

## 三、兜底：不依赖 recovery 解密的数据备份方案

见 [`docs/BACKUP-GUIDE.md`](BACKUP-GUIDE.md)。要点：

* **Android 内（已 root，正常开机）** 是唯一"能读明文 /data"的途径：`adb exec-out su -c 'tar -cf - ...'` 直接把 `/data` 相关目录流到电脑；媒体文件 `adb pull /data/media/0`。
* **recovery 内（v4.5 已可用）**：metadata 已能解开，因此可以做**分区级/裸镜像**备份（`dd` + 流式拉到电脑），包括整个 `userdata`；恢复时 `dd` 回去。限制：裸镜像只能在**同一台设备、TEE/`/persist` 状态完好**时恢复（metadata key 依赖 TEE 里的 keymaster key），所以必须同时备份 `/persist`、`metadata`、`boot`、`dtbo`、`vendor_boot`、`modem`。

## 四、电量（顺带结论）

v4.5 已生效：`ps` 里能看到 `android.hardware.health@2.1-service` 在跑 ✓（`on boot start health-hal-2-1` 起效）。
但用户实测 `cat /sys/class/power_supply/battery/capacity` → **No such file or directory**，`/sys/class/power_supply/` 是空的 → **充电器驱动模块没加载**，health HAL 只能报默认值。

v4.6 修法（二选一，建议都做）：
1. **确保 `qti_battery_charger_main.ko` 被 insmod**：TWRP 的 `TW_LOAD_VENDOR_MODULES` 路子在 recovery 里失败过（v3 日志：`Unable to open module directory: /vendor/lib/modules. Skipping`），因此更稳的做法是加一个"等待 `/vendor` 挂好后 insmod"的 oneshot 服务：
   ```rc
   service batt_mod /system/bin/sh -c "until [ -e /vendor/lib/modules/qti_battery_charger_main.ko ]; do sleep 1; done; insmod /vendor/lib/modules/qti_battery_charger_main.ko"
       oneshot
       seclabel u:r:recovery:s0
   on boot
       start batt_mod
   ```
2. **验证**：`ls /sys/class/power_supply/` 应出现 `battery`、`usb` 等；`cat /sys/class/power_supply/battery/capacity` 返回 0-100。
   若不成功（或不想做），可设 `TW_NO_BATT_PERCENT := true` **隐藏**百分比，避免显示假值 —— 不影响核心功能。

## 六、v4.7 记录（实测反馈后的修订）

### 6.1 P1：二次挂载 vfat 无效 → 改用 symlink

v4.6 的 `mkdir /vendor/firmware_mnt` + 第二次 `mount vfat` **没有生效**：
* logcat 里 `init: avc denied { create } for name="firmware_mnt" ... permissive=1` 说明 mkdir 执行了；
* 但 `ueventd : firmware: attempted /vendor/firmware_mnt/image/ipa_fws.mdt, open failed` 依旧，
  `KeymasterUtils: SPU is not available` / `verify_legacy` / `ret: -45` 也依旧。

原因：**同一个 vfat 块设备不能被二次挂载**（vfat 会拒绝），所以目录建了、内容没挂上。
v4.7 改为软链已挂载好的 `/firmware`：
```rc
rmdir /vendor/firmware_mnt
symlink /firmware /vendor/firmware_mnt
```
（ueventd 与内核 firmware loader 都会正常解析软链。）

### 6.2 P3 撤销：电量真正的修法是 v4.5 的 health 改动

实测显示**电量已经正常**，而 `mars-batt-mod.log` 里只有一行 `waiting for /vendor/lib/modules/qti_battery_charger_main.ko`
（recovery 里 `/vendor` 未挂载，模块路径不存在）。也就是说电量正常**不是**充电模块带来的，而是 v4.5 的：
* `on boot start health-hal-2-1`（health HAL 之前是 `disabled`、无人启动）；
* device manifest 声明 `android.hardware.health@2.0::IHealth/default`（2.1 的父接口，缺它 HIDL 注册会被拒）。

TWRP 的 `recovery_utils/battery_utils.cpp` 正是通过 health HAL（先 AIDL、后 HIDL `get_health_service()`）读电量，
拿不到服务时才回退到「assuming defaults」显示假值 —— 这解释了 v4.5 前后的差异。
因此 v4.7 移除了 `mars_batt_mod` 服务与 `/sbin/mars-batt-mod.sh`，避免无意义的 90 秒等待；
若将来某个 ROM 下 health HAL 也拿不到电量，再考虑 insmod（那时先确认 recovery 里 `/vendor` 的挂载时机）。
